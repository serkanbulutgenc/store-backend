# Ana sayfa is a per-user list of code-defined Widgets

The Ana sayfa is built from Widgets. Each Dashboard user keeps their own ordered list of the Widgets they have turned on, stored on the server against that user. The catalogue of Widgets is fixed in code: each Widget has a key, a permission it needs, and the data it returns. A person can turn Widgets on or off, move them up or down, and reset to the default for their role. They cannot resize, drag onto a free grid, or define a Widget of their own.

A person who has never configured gets a default for their role. A Widget added later is offered in the "add" list but stays off for anyone who already saved a layout. The server returns data only for the Widgets that are on, in order, and drops any the person no longer has permission for, so a revoked permission never leaks data through a stale layout.

We rejected an Owner-set layout (one for everyone, or one per role). It needs a settings screen and a permission to manage it, and nothing asked for it: what is useful on the Ana sayfa follows what a person does, not what they are. We also rejected a free configuration model with user-defined Widgets, saved filters or a drag-and-drop grid. It multiplies the permission and Revenue-data rules each custom Widget would have to respect, and it is hard to make accessible. Keeping the browser as the store (`localStorage`) was rejected too, because the same person uses the Dashboard on a phone and at a desk and a cleared browser would lose their setup.

Consequences: adding a Widget is a code change with its own permission and tests, not a configuration step. A Widget that shows Revenue data must be Owner-only ([Revenue data](../../GLOSSARY.md)). Because the layout is a list of keys, removing or renaming a Widget key must be handled by dropping unknown keys when the layout is read. If Owners later need to set a shared layout, it can sit above the per-user list as another default without changing how layouts are stored.
