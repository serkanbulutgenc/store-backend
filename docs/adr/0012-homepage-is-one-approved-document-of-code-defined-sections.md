# The Storefront homepage is one approved document of code-defined Sections

The Storefront home page is built from a **Homepage layout**: an ordered list of **Homepage sections**, edited in the Dashboard. Before this, the order of the eight blocks (hero, Recently viewed, three product rails, two mid banners, category rail) was hardcoded in the Storefront, and only the content inside each block was data.

**The layout is a single document for the whole shop.** It is stored as one singleton row holding an ordered JSON list. Each item has a Section type and that type's settings, validated against a per-type schema in code. It is not a table with one row per section. The layout goes live under the Approval rule ([ADR 0008](0008-staff-edits-to-published-collections-are-pending-changes.md)): Staff draft or edit it, the Owner approves, a Staff edit to the live layout waits as a Pending change, and every approved version is kept as `ApprovedVersion` history. The Owner can restore an earlier version, which creates a new one. Any Dashboard user can preview the draft or pending layout on the real Storefront. While a pending change exists the Owner approves or rejects it before editing, as for Collections.

**Section types are fixed in code.** For now: Slider, Products, Categories, Banner and Rich text. The Owner picks types, adds as many instances of each as they like (up to 20 sections), hides one without losing its settings, and sets its title, "see all" link and display style (grid, carousel or list, from those its type supports). Adding a type is a code change with its own schema and tests, not a configuration step. There is one full-width column only; a section's place is an ordered position in a single "main" region so that other arrangements can be added later without migrating stored layouts.

**Content stays where it already lives.** Slider and Banner sections point at existing Banners or at a Collection's products; they do not hold their own images, so the Banner approval flow and schedule dates are kept. A Products section takes its items from Latest, Best-selling, On sale, a Category, a hand-picked list or Recently viewed. Best-selling means units sold over a chosen window, as `sort=popular` already does. There is no server-side view tracking, so Recently viewed stays per Shopper in their own browser and its section is not rendered when the history is empty ([Recently viewed](../../GLOSSARY.md)). The Storefront gets one cached endpoint that returns the layout with each section already resolved, and the browser resolves only Recently viewed.

**Why one document, not rows.** Approval, rollback, reordering and publishing are each one write on one unit, and the layout is judged as a whole page by the Owner. `ApprovedVersion` and `PendingChange` already store a JSON payload keyed by content type and object id, so a singleton needs no new approval machinery. Per-section rows would have forced per-section approval states and partial publishes, so the live page could be a mix of approved and unapproved sections.

**Why not user-defined Sections or a free grid.** A configuration model with arbitrary blocks, custom queries or HTML needs its own permission, sanitising and accessibility rules for each block, which is the same reason [ADR 0010](0010-ana-sayfa-is-a-per-user-list-of-code-defined-widgets.md) kept the Ana sayfa to code-defined Widgets. A free grid builder was also rejected for now. Naming matters here too: "Widget" already means an Ana sayfa block, so the Storefront block is a **Section**.

**Consequences.** The document refers to other records by id (Category, Collection, Banner, Product), and those can be deleted or unpublished afterwards. References are therefore resolved when the page is read: a section whose target is gone or has nothing visible is skipped on the Storefront, and the Dashboard shows a warning on it. Storage does not enforce referential integrity. The existing hardcoded homepage is migrated into a default layout that reproduces today's eight blocks, so the Storefront looks the same on day one. The Banner Slots `home_hero` and `home_mid`, the Category `show_on_home` flag and the fixed `ana-sayfa` slug stay as content sources for now and are retired in a later release, together with the unused `StoreSettings` banner columns already marked for removal. Layouts are not per user, unlike the Ana sayfa. If scheduled sections or per-region presets are needed later, they can be added as settings of a section or a second region without changing how layouts are stored.
